# نشر النسخة المستقلة على Hostinger

هذا الدليل خاص بالمستودع الخاص `aalmkhlafi77-sudo/Abdullah-Almkhlafi-Portfolio-Clean`. لا تغيّر الموقع الأصلي أو قاعدة بياناته أو DNS أثناء الاختبار.

## 1. قاعدة بيانات جديدة ومعزولة

1. أنشئ قاعدة بيانات MySQL جديدة ومستخدماً جديداً في hPanel؛ لا تستخدم `u820178529_portfolio` ولا مستخدمها القديم.
2. افتح القاعدة الجديدة فقط في phpMyAdmin، واستورد `server/db/schema.sql` من هذا المستودع. ينشئ الجداول الستة ولا يضع مسودة `{}`. لا تستورد نسخة SQL قديمة إلى هذه القاعدة في اختبار النسخة النظيفة.
3. تأكد أن الجداول الستة موجودة وأن `admins` فارغة قبل إنشاء المسؤول الأول. عند **أول تشغيل فقط**، يضيف التطبيق سجل `main_site` بمسودة ومنشور مكتملين من `src/data/initialData.ts`، ويضيف الإصدار الأول إلى `content_versions`. بعد بدء التطبيق، تحقق من وجود السجل والصفحات، ثم شغّل `npm run db:check` إن توفرت لك وحدة تشغيل. هذا الفحص يقرأ القاعدة ولا يغيّرها.

التطبيق **لا ينشئ الجداول تلقائياً**. إذا لم يُستورد المخطط، يفشل بدء الخادم عند تهيئة المحتوى. لا تعتمد على بدء العملية أو `/api/health` وحده دليلاً على ظهور الصفحات. تهيئة `main_site` مشروطة بعدم وجود السجل، أو بوجود سجل `{}` لم يُحفظ ولم يُنشر مطلقًا (`draft_version=0` و`published_version=0`). مسودة فارغة حُفظت عمدًا لا تُعبأ مجددًا عند Build أو Restart أو Deploy.

## 2. تطبيق تجريبي من نوع Web App

عند إنشاء موقع جديد بعد دمج التغييرات المعتمدة، اربط **Web App** بنطاق مؤقت من مستودع GitHub وفرع `main`. الموقع التجريبي الحالي يبقى مرتبطًا بفرعه التجريبي؛ نشر فرع الإصلاح عليه يحتاج موافقة مستقلة قبل اختبار القبول الحي. لا تستخدم PHP/HTML أو نشر الملفات داخل `public_html`.

| الحقل | القيمة |
|---|---|
| Framework | Express |
| Node.js | 22.x |
| Root directory | `./`؛ `package.json` في جذر المستودع |
| Package manager | npm |
| Build command، إن ظهر | `npm run build` |
| Entry file | `dist-server/index.js` |
| Output directory، إن ظهر | فارغ |
| Start command، إن ظهر | `npm start` |

قد لا تعرض واجهة Hostinger حقول أمر البناء والتشغيل. يتحقق سجل النشر من `npm run build`، ويُنشئ `dist` و`dist-server/index.js`؛ وسكربت `start` في `package.json` يشغّل الملف الناتج.

## 3. متغيرات التشغيل داخل hPanel

أدخل القيم في **Environment variables** للتطبيق الجديد فقط؛ لا تضع كلمة مرور حقيقية في GitHub أو ملف `.env` منشور أو المحادثة:

```text
NODE_ENV=production
PUBLIC_ORIGIN=https://النطاق-المؤقت-الفعلي
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=اسم-القاعدة-الجديدة
DB_USER=مستخدم-القاعدة-الجديد
DB_PASSWORD=كلمة-مرور-المستخدم-داخل-hPanel-فقط
TRUST_PROXY=1
UPLOAD_ROOT=/home/معرّف-الحساب/domains/النطاق-المؤقت-الفعلي/media
INITIAL_ADMIN_USERNAME=اسم-مسؤول-جديد
INITIAL_ADMIN_PASSWORD=كلمة-مرور-فريدة-من-12-حرفاً-على-الأقل
```

`APP_URL` ليس بديلاً عن `PUBLIC_ORIGIN`. طابق الأخير مع أصل عنوان التطبيق `https://...` دون شرطة مائلة أو مسار؛ وإلا سترفض حماية الطلبات تسجيل الدخول والحفظ. استعمل `DB_HOST=127.0.0.1` فقط حين يعمل MySQL على خادم الاستضافة نفسه، كما ثبت في اختبار Hostinger السابق؛ إن خصّصت Hostinger خادماً مختلفاً للقاعدة الجديدة فاتبع بيانات اتصالها. لا تثبت `PORT` يدوياً إذا زوّدته المنصة؛ الخادم يقرأه ويستمع على `0.0.0.0`.

أنشئ مجلد `media` الدائم في المسار الذي أدخلته، وتحقق من قابلية الكتابة. يجب أن يبقى **خارج** `public_html` و`hbuilds` و`versions` و`last-source`؛ لا تستخدم مجلد `server/media`، فهو شيفرة المصدر لا مكان الصور. المسار الدائم غير موجود تلقائياً لمجرد إضافة المتغير.
يرفض الخادم إعداد `UPLOAD_ROOT` الذي يتضمن أحد مجلدات النشر الأربعة المذكورة. تحقق أيضًا من المسار الفعلي في hPanel، خاصة إذا كان رابطًا رمزيًا، ومن استمرار وجوده بعد إعادة نشر Web App.

بعد إنشاء أول مسؤول احذف متغيرَي `INITIAL_ADMIN_USERNAME` و`INITIAL_ADMIN_PASSWORD` من hPanel وأعد تشغيل التطبيق. تغييرهما لاحقاً **لا يغير كلمة مرور مسؤول موجود**. لا تستخدم كلمة مرور قاعدة البيانات لتسجيل الدخول للوحة التحكم.

## 4. اختبار قبول قبل نقل النطاق

1. تحقق من أن `/api/health` يعيد JSON `{"ok":true,"database":"ready"}`، لا صفحة HTML.
2. سجل الدخول بالمسؤول الجديد؛ عند الفشل افحص حالة `/api/auth/login` وسجل التشغيل: `401` بيانات اعتماد مرفوضة، `403` عدم تطابق `PUBLIC_ORIGIN`، `429` حد المحاولات، `500` خطأ بالخادم/القاعدة.
3. عدّل نصاً، احفظ المسودة، حدّث الصفحة وتأكد من بقائه. انشر وافتح من نافذة خاصة/جهاز ثانٍ للتأكد من ظهور المنشور.
4. ارفع صورة؛ يجب أن يكون رابطها `/media/...`، وأن تظهر بعد إعادة تشغيل التطبيق وإعادة النشر، مع وجود الملف في `UPLOAD_ROOT`. الملف غير الصالح يعيد `400`، وتعطل التخزين أو قاعدة البيانات أثناء الرفع يعيد `500` دون الإبقاء على ملف رفع جزئي.
5. تحقّق أن المحتوى لا يعود بعد الحذف أو الاستبدال، وأن تسجيل الخروج يوقف الوصول لمسارات الإدارة.
6. عطّل الاتصال مؤقتًا أو افحص استجابة API معطلة: ينبغي أن تعرض الواجهة حالة تعذر تحميل المحتوى، وألا تعرض نسخة قديمة محفوظة في المتصفح. عند فتح المسودة من جلستين، يجب أن يرفض الخادم حفظ الإصدار القديم بتعارض `409`.
7. راجع سجل البناء والتشغيل ونتائج CI و`npm audit --omit=dev --audit-level=high`. البناء يقسم أدوات الإدارة ومكتبة الأيقونات؛ قد يستمر تحذير Vite لحزمة كبيرة، لذا راقب حجم التحميل على النطاق المؤقت.

القاعدة الجديدة تبدأ بمحتوى GitHub الافتراضي الكامل بعد أول تشغيل، لكن يجب التأكد من عدد الصفحات والعناصر في الواجهة العامة والمصمم، ثم فحص الحفظ والنشر والصور فعليًا. لا تنقل بيانات النسخ الاحتياطية القديمة إلا بقرار منفصل وبعد فحصها.

### ترحيل الموقع التجريبي الذي سبق أن بدأ بمسودة فارغة

التطبيق **لا يملأ** الموقع التجريبي الحالي تلقائيًا؛ فقد أصبح له إصدارات محفوظة ومنشورة وصورتان من الاختبار. بعد الموافقة على نشر فرع الإصلاح على **النطاق التجريبي فقط**:

1. صدّر مسودته الحالية من الواجهة قبل استبدالها، واحتفظ بنسختها خارج المستودع.
2. افتح «الإعدادات ← النسخ الاحتياطي»، واختر ملف JSON القديم من جهازك. لا تضفه إلى Git ولا إلى مجلد النشر. اقبل المعاينة فقط إن طابقت أعداد الصفحات والعناصر والمشاريع والصور المتوقعة.
3. ضع علامة تأكيد استبدال المسودة واضغط الاستيراد. صيغة `timestamp` القديمة تتحول إلى `schemaVersion=1` و`savedAt`؛ يُستكمل `heroConfig` من إعدادات GitHub و`brandVideoUrl` الافتراضي، ويُعرض ذلك في المعاينة. لا تُنشأ قيم بديلة صامتة لقوائم المحتوى الناقصة. تُنقل الصور المضمّنة إلى `UPLOAD_ROOT` الدائم، وتُحفظ روابط `/media/` في المسودة.
4. حدّث الصفحة وتحقق من المسودة والصور، ثم انشر يدويًا وافحص النتيجة بلا جلسة. أعد تشغيل التطبيق وأعد نشر **الفرع التجريبي نفسه** ثم افحص الصفحات وروابط الصور. لا يستبدل الاستيراد المنشور قبل ضغط «نشر».

إذا عاد تعارض `409`، احتفظ بالتعديلات المحلية وأعد تحميل أحدث مسودة بعد حفظ ما يلزم؛ لا تتجاوز رقم الإصدار. إذا فشل التخزين أو قاعدة البيانات، لا تُعرض رسالة نجاح ولا تُستبدل المسودة. استبدال المسودة قد يزيل الصورتين التجريبيتين من قائمة المكتبة إذا لم تكونا في النسخة المختارة؛ نسخة المسودة السابقة تحفظ مرجعهما للمراجعة قبل الإجراء.

## 5. نقل النطاق لاحقاً

لا تحذف الموقعين القديمين ولا تغيّر `almkhlafi.carpetbazar.org` الآن. بعد نجاح الاختبارات وتوثيق الرجوع، افصل ارتباط النطاق من الموقع القديم بالطريقة التي تدعمها hPanel واربطه بتطبيق Web App الجديد، ثم حدّث `PUBLIC_ORIGIN` إلى `https://almkhlafi.carpetbazar.org` وأعد التشغيل. أعد اختبار الصحة والدخول والحفظ والصور على النطاق الفعلي. احتفظ بالنسخة القديمة وقواعدها للرجوع حتى تثبت الاستقرار.
