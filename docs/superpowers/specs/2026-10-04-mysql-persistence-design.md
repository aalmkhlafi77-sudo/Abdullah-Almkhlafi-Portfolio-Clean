# تصميم ترحيل موقع عبدالله المخلافي إلى Express وMySQL

**التاريخ:** 2026-10-04  
**المستودع:** `aalmkhlafi77-sudo/Abdullah-Almkhlafi-Portfolio`  
**الفرع:** `feature/mysql-persistence-v1`  
**الحالة:** تصميم معتمد مبدئيًا، والتنفيذ لا يبدأ قبل مراجعة هذه الوثيقة.

## 1. الهدف

تحويل حفظ وتحرير محتوى الموقع من الاعتماد على `localStorage` وFirebase إلى خادم خلفي آمن داخل Hostinger يستخدم Express وMySQL، مع المحافظة على شكل الموقع وجميع أدوات التحرير الحالية وعدم تعطيل أي وظيفة تعمل.

يُعد الإصلاح ناجحًا عندما:

- يرى جميع الزوار المحتوى المنشور نفسه من أي جهاز.
- تُحفظ المسودة في MySQL ولا تظهر للزوار قبل النشر.
- يؤدي النشر إلى تحديث المحتوى العام بصورة ذرّية ونهائية.
- لا تعرض الواجهة رسالة نجاح إذا فشل الحفظ في الخادم.
- لا تُخزن كلمة مرور الإدارة أو حالة الدخول في `localStorage`.
- يمكن استيراد النسخة الحالية دون فقد النصوص أو الصفحات أو المشاريع أو المقالات أو الخدمات أو الصور.
- يمكن الرجوع إلى إصدار منشور سابق من سجل الإصدارات.
- يبقى الموقع الحالي عاملًا حتى نجاح النسخة التجريبية.

## 2. السبب الجذري

يبدأ `src/context/AppContext.tsx` حاليًا بقراءة البيانات من `localStorage`، ثم يحاول مزامنتها مع Firestore. عند نفاد الحصة أو انتهاء المهلة يستمر الحفظ محليًا، وقد تظهر رسائل نجاح رغم عدم وجود نسخة دائمة مشتركة بين الأجهزة. كما تُخزن بيانات دخول الإدارة وحالة تسجيل الدخول داخل المتصفح.

إنشاء قاعدة MySQL وحده لا يغيّر هذا السلوك؛ يجب تبديل مسار القراءة والكتابة والمصادقة داخل التطبيق.

## 3. الحدود

### ضمن الإصدار

- خادم Express يقدم واجهات `/api` ويقدم ملفات Vite المبنية من `dist`.
- اتصال MySQL عبر متغيرات بيئة Hostinger.
- دخول وخروج وتغيير كلمة مرور الإدارة.
- قراءة المحتوى المنشور.
- قراءة وحفظ المسودة.
- نشر المسودة مع إنشاء نسخة تاريخية.
- استيراد وتصدير نسخة JSON.
- رفع الصور وحذف غير المستخدمة منها.
- سجل تدقيق للعمليات الحساسة.
- ترحيل آمن من JSON والتخزين المحلي القديم.
- إزالة Firebase والتخزين المحلي الدائم بعد إثبات نجاح الترحيل.
- نشر تجريبي من GitHub قبل تحويل الموقع الحالي.

### خارج الإصدار

- تغيير التصميم المرئي أو ترتيب الأقسام.
- إعادة كتابة منشئ الصفحات.
- إضافة أدوار متعددة للمسؤولين.
- رفع الفيديوهات الكبيرة؛ تبقى الفيديوهات روابط خارجية في هذا الإصدار.
- تحويل المحتوى المرن إلى جداول منفصلة لكل نوع؛ تبقى لقطة الموقع JSON لتجنب فقد الحقول الحالية.

## 4. البنية

### الواجهة

تبقى React/Vite كما هي. يُضاف عميل API واحد مسؤول عن:

- تحميل المحتوى المنشور عند بدء الموقع.
- فحص جلسة الإدارة.
- حفظ المسودة ونشرها.
- استيراد وتصدير النسخ.
- رفع الصور.

لا تتصل مكونات الواجهة مباشرة بقاعدة البيانات، ولا تحتوي على معلومات اتصال MySQL.

### الخادم

تُقسم مسؤوليات الخادم إلى وحدات صغيرة:

- `server/app.ts`: إنشاء تطبيق Express والوسائط والمسارات.
- `server/index.ts`: بدء الخادم والاستماع إلى `PORT`.
- `server/config.ts`: قراءة متغيرات البيئة والتحقق منها.
- `server/db.ts`: حوض اتصالات MySQL.
- `server/auth/*`: الجلسات وتجزئة كلمات المرور وحماية المسارات.
- `server/content/*`: قراءة المسودة وحفظها ونشرها والإصدارات.
- `server/media/*`: رفع الصور وبياناتها وحذفها الآمن.
- `server/audit/*`: سجل العمليات.
- `server/migration/*`: التحقق من نسخة JSON وتحويل الصور المضمّنة.

### قاعدة البيانات

الجداول المنشأة والمعتمدة:

- `admins`
- `admin_sessions`
- `site_documents`
- `content_versions`
- `media_files`
- `audit_logs`

السجل `site_documents.document_key = 'main_site'` هو المستند الرئيسي. يحتوي:

- `draft_json`: آخر مسودة محفوظة.
- `published_json`: المحتوى العام المعتمد.
- `draft_version`: رقم المسودة.
- `published_version`: رقم النشر.

## 5. نموذج المحتوى

تستخدم الواجهة والخادم النوع المنطقي `PortfolioSnapshotV1`، ويشمل:

- `schemaVersion: 1`
- `profile`
- `metrics`
- `services`
- `solutions`
- `projects`
- `articles`
- `mediaList`
- `pages`
- `showcaseApps`
- `showcaseBarConfig`
- `cvResumeData`
- `heroConfig`
- `brandVideoUrl`
- `savedAt`

لا تُقبل بيانات دخول الإدارة ضمن المحتوى. يتحقق الخادم من أن الجذر كائن JSON، ومن النسخة والحجم والحقول الأساسية قبل الحفظ.

## 6. واجهات API

### عامة

- `GET /api/health`: حالة الخادم وقاعدة البيانات دون كشف أسرار.
- `GET /api/public/content`: إرجاع `published_json` ورقم الإصدار ووقت النشر. إذا لم يوجد نشر بعد يعيد حالة واضحة ولا يستبدل المحتوى تلقائيًا.

### المصادقة

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `PUT /api/auth/password`

### الإدارة

- `GET /api/admin/content/draft`
- `PUT /api/admin/content/draft`
- `POST /api/admin/content/publish`
- `POST /api/admin/content/import`
- `GET /api/admin/content/export`
- `POST /api/admin/content/restore/:version`
- `POST /api/admin/media`
- `DELETE /api/admin/media/:id`

جميع مسارات الإدارة، عدا تسجيل الدخول، تتطلب جلسة صالحة.

## 7. الحفظ والنشر

### حفظ المسودة

1. تجمع الواجهة لقطة كاملة من الحالة الحالية.
2. ترسل اللقطة مع `expectedDraftVersion`.
3. يتحقق الخادم من الجلسة والبيانات والحجم.
4. ينفذ تحديثًا مشروطًا داخل MySQL.
5. إذا تغير الإصدار في جهاز آخر يعيد `409 Conflict` ولا يكتب فوقه.
6. عند النجاح يعيد رقم الإصدار الجديد.
7. لا تغير الواجهة حالة المسودة إلى «محفوظة» إلا بعد استلام نجاح الخادم.

### النشر

1. يفتح الخادم معاملة MySQL.
2. يقفل سجل `main_site`.
3. ينسخ المسودة الحالية إلى `published_json`.
4. ينشئ سجلًا في `content_versions`.
5. يحدث رقم الإصدار ووقت النشر.
6. يسجل العملية في `audit_logs`.
7. يعتمد المعاملة كاملة أو يتراجع عنها كاملة.

يقرأ الزوار `published_json` فقط، لذلك لا تظهر التعديلات غير المنشورة.

## 8. المصادقة والأمان

- تُجزأ كلمات المرور بواسطة `bcryptjs` ولا تُحفظ كنص صريح.
- تُنشأ جلسة عشوائية باستخدام `crypto.randomBytes(32)`.
- يُخزن تجزئة معرّف الجلسة في `admin_sessions`.
- ترسل الجلسة في Cookie بخصائص `HttpOnly` و`Secure` و`SameSite=Strict`.
- مدة الجلسة الافتراضية 8 ساعات.
- تُلغى الجلسات المنتهية دوريًا وعند تسجيل الخروج أو تغيير كلمة المرور.
- تُفحص ترويسة `Origin` للطلبات المعدلة للحماية من CSRF.
- يُطبق تحديد للمحاولات على تسجيل الدخول.
- لا تظهر تفاصيل قاعدة البيانات أو الأخطاء الداخلية في الردود العامة.
- لا تدخل كلمات المرور أو مفاتيح الجلسات أو إعدادات الإنتاج إلى GitHub.
- ينشأ أول مسؤول بأمر إعداد لمرة واحدة يعتمد على متغيرات بيئة Hostinger، ثم تُحذف قيمة كلمة المرور الأولية من الإعدادات.

## 9. الوسائط

- الصور المقبولة: JPEG وPNG وWebP وGIF.
- الحد الأقصى للصورة 10 ميجابايت.
- يتحقق الخادم من النوع الفعلي والامتداد ويولد اسمًا عشوائيًا.
- تحفظ الملفات في مسار دائم خارج مجلد النشر يحدده `UPLOAD_ROOT`.
- يقدم الخادم الملفات من مسار `/media/*`.
- يخزن جدول `media_files` البيانات الوصفية والرابط.
- لا يحذف ملف مستخدم داخل المحتوى المنشور.
- لا تُحفظ صور `blob:` أو Base64 في المحتوى النهائي.

## 10. نقل البيانات الحالية

1. تبقى نسخة `public_html` والنسخة JSON الحالية محفوظتين.
2. تُنشر النسخة الجديدة على عنوان تجريبي مرتبط بفرع الميزة.
3. يسجل المسؤول الدخول بحساب الخادم الجديد.
4. تُرفع نسخة JSON من لوحة الإدارة.
5. يتحقق الخادم منها ويحوّل صور `data:image/*` إلى ملفات دائمة ويستبدل الروابط.
6. تُحفظ النسخة أولًا كمسودة.
7. يعرض الموقع التجريبي المسودة للمسؤول فقط.
8. بعد الفحص تُنشر المسودة.
9. عند تشغيل النسخة الجديدة على النطاق الأصلي، يكتشف التطبيق مفاتيح التخزين المحلية القديمة في متصفح المسؤول فقط ويعرض أمر دمج صريح للحقول غير الموجودة، ومنها `heroConfig` و`brandVideoUrl`.
10. لا يجري أي دمج أو استبدال تلقائي.
11. بعد التحقق من جهاز ثانٍ تُحذف مسارات Firebase وبيانات الدخول القديمة ومفاتيح المحتوى الدائم من المتصفح. يبقى التخزين المحلي للمظهر ومسودة تعافٍ قصيرة العمر فقط.

## 11. سلوك الفشل

- فشل تحميل المحتوى العام: يعرض آخر نسخة منشورة مخبأة للقراءة فقط مع تنبيه اتصال، ولا يعود إلى محتوى افتراضي قديم إذا سبق وجود نشر.
- فشل حفظ المسودة: تبقى الحالة «غير محفوظة» وتظهر رسالة خطأ واضحة.
- تعارض إصدار: لا يحدث استبدال صامت؛ يطلب إعادة تحميل المسودة الأحدث.
- فشل النشر: تبقى النسخة العامة السابقة سليمة.
- فشل رفع صورة: لا تُضاف الصورة إلى مكتبة الوسائط.
- تعطل قاعدة البيانات: يعيد `503` ولا يعرض نجاحًا وهميًا.

## 12. الاختبارات

تُكتب الاختبارات قبل التنفيذ باستخدام `node:test` مع فصل مستودعات البيانات لحقن بدائل اختبارية.

الحد الأدنى:

- رفض المحتوى غير الصحيح أو الأكبر من الحد.
- عدم قبول بيانات دخول ضمن لقطة المحتوى.
- فشل الدخول بكلمة مرور خاطئة ونجاح الصحيحة.
- انتهاء الجلسة وإلغاؤها عند الخروج وتغيير كلمة المرور.
- رفض مسارات الإدارة دون جلسة.
- كشف تعارض رقم المسودة وإرجاع 409.
- حفظ المسودة دون تغيير المنشور.
- نشر ذري وإنشاء نسخة تاريخية وسجل تدقيق.
- بقاء المنشور السابق عند فشل المعاملة.
- تحويل صور Base64 أثناء الاستيراد ورفض `blob:`.
- منع حذف صورة مستخدمة.
- عدم عرض نجاح في الواجهة عند رد 4xx أو 5xx.
- نجاح `npm run lint` و`npm test` و`npm run build`.

## 13. النشر

- يبقى `main` والموقع الحالي دون تغيير أثناء التطوير.
- ينفذ العمل على `feature/mysql-persistence-v1`.
- يربط Hostinger فرع الميزة بتطبيق تجريبي React/Vite + Express.
- إعداد البناء: `npm install` ثم `npm run build`.
- أمر التشغيل: `npm start`.
- متغيرات الإنتاج تُدخل في Hostinger فقط:
  - `NODE_ENV`
  - `PORT` من Hostinger
  - `DB_HOST`
  - `DB_PORT`
  - `DB_NAME`
  - `DB_USER`
  - `DB_PASSWORD`
  - `UPLOAD_ROOT`
  - `PUBLIC_ORIGIN`
  - متغيرات إعداد المسؤول الأول لمرة واحدة
- بعد نجاح الاختبارات الوظيفية والبصرية من جهازين يُدمج الفرع إلى `main`.
- يربط النطاق الأصلي بالتطبيق الجديد أو يحول نشره إليه.
- كل دفع لاحق إلى الفرع المرتبط يشغل إعادة نشر آلية.

## 14. التحقق قبل التحويل

لا يتحول النطاق قبل نجاح جميع البنود:

- `/api/health` يؤكد اتصال MySQL.
- تسجيل الدخول والخروج وتغيير كلمة المرور.
- استيراد النسخة دون أخطاء.
- تطابق الصفحة العامة بصريًا مع الحالية.
- تعديل نص وصورة وخدمة ومقال ومشروع.
- حفظ المسودة دون ظهورها للزائر.
- نشرها وظهورها في نافذة خاصة وجهاز ثانٍ.
- إعادة التحميل دون رجوع العناصر القديمة.
- حذف عنصر والتأكد من بقائه محذوفًا بعد إعادة التحميل.
- رفع صورة واستبدالها والتحقق من عدم استخدام Base64.
- عدم وجود طلبات Firebase في أدوات المطور بعد الإغلاق النهائي.
- نجاح النسخ الاحتياطي والتصدير والاستعادة.

## 15. الرجوع الآمن

- تبقى نسخة `public_html` الحالية متاحة حتى نهاية التحقق.
- إذا فشل التطبيق الجديد يعاد توجيه النطاق إلى الموقع الحالي.
- لا تُحذف قاعدة البيانات عند الرجوع.
- لا تُمسح بيانات المتصفح ولا Firebase قبل نجاح التحقق من جهاز ثانٍ.
- لا يُحذف فرع الترحيل حتى مرور فترة مراقبة بعد الإنتاج.
